# Спецификации вариантов использования «RhythmSpace»

**Проект:** веб-приложение для школы танцев «RhythmSpace»
**Версия:** 1.0
**Автор:** Лукашевич А.Д.
**Дата:** 22.11.2026
**Диаграмма:** [diagrams/use-case-diagram.png](diagrams/use-case-diagram.png)
**Связанные документы:** [SRS](srs/srs1.1.md), [glossary.md](glossary.md), [SDD](sdd/sdd.md)

Документ содержит описания актёров и прецедентов (разделы 1–3 и UC-01…UC-13) и дополнительные спецификации (последний раздел).

## 1. Как читать описание

Каждый прецедент описан по одной схеме: **пояснение** (зачем нужен), **актёры**, **предусловия**, **триггер**, **основной поток**, **альтернативные потоки**, **постусловия**, **трассировка** на требования SRS. Идентификаторы `UC-NN` совпадают с подписями на диаграмме прецедентов.

Обозначения связей на диаграмме:

- сплошная стрелка от актёра к прецеденту: актёр инициирует прецедент;
- пунктирная стрелка с подписью «include»: прецедент всегда использует поведение другого;
- пунктирная стрелка без подписи UC-03 → UC-04: обязательная проверка мест внутри записи (по смыслу тоже включение);
- сплошная стрелка между прецедентом и базой данных: прецедент читает данные из БД.

## 2. Актёры

| Актёр | Тип | Описание роли в системе |
|---|---|---|
| Пользователь | Человек | Ученик школы танцев, который работает с приложением через браузер: смотрит расписание, записывается на занятия и отменяет запись, ведёт профиль, пишет в чат. |
| База данных | Внешняя система | Хранилище PostgreSQL: отдаёт прецеденту UC-02 данные расписания и участвует в проверке свободных мест в UC-04. |

> Администратор (SRS 2.4) в этой итерации модели не выделен: на диаграмму вынесены сценарии, с которыми работает ученик. Сценарии администратора (управление расписанием, ответы в чате) будут добавлены отдельной диаграммой.

## UC-01: Зарегистрироваться

- **Пояснение:** создаёт учётную запись ученика, без которой нельзя записываться на занятия и вести профиль.
- **Актёры:** Пользователь.
- **Предусловия:** пользователь не имеет учётной записи; открыта страница регистрации.
- **Триггер:** пользователь нажимает «Регистрация».
- **Основной поток:**
  1. Система показывает форму (имя, email, пароль).
  2. Пользователь заполняет поля и нажимает «Зарегистрироваться».
  3. Система проверяет формат email и надёжность пароля.
  4. Система проверяет, что email ещё не занят.
  5. Система сохраняет хеш пароля (BCrypt) и создаёт пользователя с ролью «Ученик».
  6. Система сообщает об успехе и предлагает войти.
- **Альтернативные потоки:**
  - А1. Email уже зарегистрирован: сообщение «Пользователь с таким email уже существует», форма остаётся открытой.
  - А2. Данные не прошли проверку: подсвечиваются ошибочные поля, запись не создаётся.
- **Постусловия:** в системе есть учётная запись ученика с уровнем подготовки по умолчанию.
- **Трассировка:** REQ-FUNC-001, REQ-SEC-001, REQ-COMP-001.

## UC-02: Просмотреть расписание

- **Пояснение:** главный экран приложения: список предстоящих занятий выбранного филиала со временем, направлением, преподавателем и числом свободных мест.
- **Актёры:** Пользователь; База данных (источник данных).
- **Предусловия:** выбран филиал (по умолчанию первый в списке). Вход в систему не требуется.
- **Триггер:** пользователь открывает экран «Расписание».
- **Основной поток:**
  1. Пользователь открывает экран «Расписание».
  2. Система запрашивает у БД занятия выбранного филиала.
  3. База данных возвращает занятия с признаком вместимости и числом броней.
  4. Система отображает карточки занятий и число свободных мест.
- **Альтернативные потоки:**
  - А1. Занятий на ближайший период нет: система показывает сообщение «Занятий нет».
  - А2. БД недоступна: сообщение об ошибке загрузки, предложение повторить.
- **Постусловия:** пользователь видит актуальное расписание филиала.
- **Трассировка:** REQ-FUNC-002, REQ-INT-001, REQ-PERF-001, REQ-INT-004.

## UC-03: Записаться на групповое занятие

- **Пояснение:** основной бизнес-сценарий: ученик занимает место в группе. Включает авторизацию (UC-07) и проверку свободных мест (UC-04).
- **Актёры:** Пользователь.
- **Предусловия:** занятие находится в расписании (UC-02); пользователь выбрал занятие.
- **Триггер:** пользователь нажимает «Записаться» на карточке занятия.
- **Основной поток:**
  1. Пользователь нажимает «Записаться».
  2. Система проверяет, авторизован ли пользователь (UC-07).
  3. Клиент отправляет запрос на запись.
  4. Система находит занятие и проверяет наличие мест (UC-04).
  5. Система создаёт запись со статусом «Активна» и увеличивает `booked_count` в одной транзакции.
  6. Система показывает сообщение «Вы записаны» и обновляет число свободных мест.
- **Альтернативные потоки:**
  - А1. Пользователь не авторизован: перенаправление на страницу входа (после входа сценарий можно продолжить).
  - А2. Свободных мест нет: сообщение «Свободных мест нет» и предложение выбрать другое занятие.
  - А3. Конфликт версий (последнее место занял другой ученик): транзакция откатывается, пользователю предлагается повторить попытку.
- **Постусловия:** создана запись; число свободных мест уменьшилось на единицу.
- **Трассировка:** REQ-FUNC-003, REQ-FUNC-007, REQ-SEC-002; SDD 2.2.12 (оптимистичная блокировка).

## UC-04: Проверить наличие свободных мест

- **Пояснение:** вложенный сценарий записи: сравнивает число броней занятия с его вместимостью. Самостоятельно пользователем не запускается.
- **Актёры:** База данных (источник `booked_count` и `max_students`).
- **Предусловия:** выбрано занятие (идёт выполнение UC-03).
- **Триггер:** сервис записи запрашивает проверку мест.
- **Основной поток:**
  1. Сервис запрашивает занятие у репозитория.
  2. База данных возвращает данные занятия.
  3. Сервис сравнивает `booked_count` с `max_students`.
  4. Если `booked_count < max_students`, сервис возвращает признак «места есть».
- **Альтернативные потоки:**
  - А1. `booked_count >= max_students`: возвращается признак «мест нет», запись не создаётся.
  - А2. Занятие не найдено: возвращается ошибка «Занятие не существует».
- **Постусловия:** принято решение, продолжать ли запись.
- **Трассировка:** REQ-FUNC-007.

## UC-05: Записаться на индивидуальное занятие

- **Пояснение:** ученик занимает свободное время выбранного тренера для персонального занятия.
- **Актёры:** Пользователь.
- **Предусловия:** пользователь авторизован (UC-07); у тренера есть свободное время.
- **Триггер:** пользователь выбирает тренера и нажимает «Индивидуальное занятие».
- **Основной поток:**
  1. Пользователь открывает карточку преподавателя (UC-13).
  2. Пользователь нажимает «Индивидуальное занятие».
  3. Система показывает свободное время тренера.
  4. Пользователь выбирает слот и подтверждает.
  5. Система проверяет, что слот ещё свободен, и создаёт запись.
  6. Система показывает подтверждение и добавляет занятие в «Мои занятия».
- **Альтернативные потоки:**
  - А1. Свободного времени нет: сообщение и предложение выбрать другого тренера.
  - А2. Слот занят другим учеником: сообщение, список слотов обновляется.
  - А3. Пользователь не авторизован: переход к UC-07.
- **Постусловия:** слот тренера закреплён за учеником.
- **Трассировка:** REQ-FUNC-009.

## UC-06: Отменить запись

- **Пояснение:** ученик отказывается от занятия, и место возвращается в группу.
- **Актёры:** Пользователь.
- **Предусловия:** пользователь авторизован (UC-07); у него есть запись со статусом «Активна».
- **Триггер:** пользователь нажимает «Отменить запись» на экране «Мои занятия».
- **Основной поток:**
  1. Пользователь выбирает активную запись и нажимает «Отменить запись».
  2. Система запрашивает подтверждение.
  3. Пользователь подтверждает.
  4. Система меняет статус записи на «Отменена учеником».
  5. Система уменьшает `booked_count` занятия.
  6. Система сообщает об отмене и обновляет список.
- **Альтернативные потоки:**
  - А1. Пользователь отказался от подтверждения: запись остаётся активной.
  - А2. Занятие уже прошло: отмена недоступна, кнопка скрыта.
- **Постусловия:** запись отменена, место снова свободно.
- **Трассировка:** REQ-FUNC-003, REQ-INT-002.

## UC-07: Авторизоваться

- **Пояснение:** вход по email и паролю. Подключается к прецедентам, которые требуют личной учётной записи (записаться, отменить запись).
- **Актёры:** Пользователь.
- **Предусловия:** у пользователя есть учётная запись (UC-01); активной сессии нет.
- **Триггер:** пользователь нажимает «Войти» либо защищённое действие переадресует его на вход.
- **Основной поток:**
  1. Система показывает форму входа.
  2. Пользователь вводит email и пароль.
  3. Система находит пользователя и сверяет пароль с BCrypt-хешем.
  4. Система выдаёт JWT-токен.
  5. Система возвращает пользователя к действию, с которого начался вход.
- **Альтернативные потоки:**
  - А1. Неверный email или пароль: сообщение «Неверный email или пароль», форма остаётся открытой.
  - А2. Пользователь не зарегистрирован: переход к UC-01.
- **Постусловия:** создана сессия, токен выдан, доступны защищённые прецеденты.
- **Трассировка:** REQ-FUNC-001, REQ-SEC-001, REQ-SEC-002.

## UC-08: Написать администратору в чате

- **Пояснение:** быстрая связь ученика с администратором без выхода из приложения.
- **Актёры:** Пользователь.
- **Предусловия:** пользователь авторизован; работает WebSocket-соединение.
- **Триггер:** пользователь открывает виджет чата на экране «Мои занятия».
- **Основной поток:**
  1. Пользователь открывает виджет чата.
  2. Система устанавливает WebSocket-соединение и подгружает историю переписки.
  3. Пользователь вводит текст и отправляет сообщение.
  4. Система доставляет сообщение администратору в реальном времени.
  5. Ответ администратора появляется в окне чата.
- **Альтернативные потоки:**
  - А1. Соединение потеряно: чат пытается переподключиться, остальной интерфейс не блокируется.
  - А2. Пустое сообщение: отправка блокируется.
- **Постусловия:** сообщение доставлено и сохранено в истории переписки.
- **Трассировка:** REQ-FUNC-010, REQ-INT-007, REQ-REL-001.

## UC-09: Просмотреть историю посещений

- **Пояснение:** список занятий, на которых ученик действительно был; основа для статистики прогресса.
- **Актёры:** Пользователь.
- **Предусловия:** пользователь авторизован.
- **Триггер:** пользователь открывает блок «История посещений» на экране «Мои занятия».
- **Основной поток:**
  1. Пользователь открывает блок «История посещений».
  2. Система загружает записи со статусом «Посещена».
  3. Система показывает занятия с датой, направлением и преподавателем.
- **Альтернативные потоки:**
  - А1. Посещений ещё нет: показывается подсказка «Здесь появятся ваши занятия».
- **Постусловия:** ученик видит список посещённых занятий.
- **Трассировка:** REQ-FUNC-004, REQ-INT-002.

## UC-10: Просмотреть профиль и прогресс

- **Пояснение:** личная страница ученика: уровень подготовки, число посещений, достижения.
- **Актёры:** Пользователь.
- **Предусловия:** пользователь авторизован.
- **Триггер:** пользователь открывает «Мои занятия» или «Профиль».
- **Основной поток:**
  1. Пользователь открывает профиль.
  2. Система загружает данные профиля и список достижений.
  3. Система считает статистику посещений.
  4. Система показывает уровень подготовки, статистику и достижения.
- **Альтернативные потоки:**
  - А1. Достижений нет: отображается пустое состояние с пояснением.
- **Постусловия:** ученик видит актуальный профиль и трекер прогресса.
- **Трассировка:** REQ-FUNC-004, REQ-INT-002.

## UC-11: Выбрать филиал

- **Пояснение:** ограничивает расписание одной студией сети.
- **Актёры:** Пользователь.
- **Предусловия:** открыта главная страница; в системе есть хотя бы один филиал.
- **Триггер:** пользователь открывает список филиалов.
- **Основной поток:**
  1. Система показывает список филиалов с адресами.
  2. Пользователь выбирает филиал.
  3. Система запоминает выбор и обновляет расписание.
- **Альтернативные потоки:**
  - А1. У филиала нет занятий: показывается сообщение «Занятий нет».
- **Постусловия:** расписание показывает занятия выбранного филиала.
- **Трассировка:** REQ-FUNC-005.

## UC-12: Отфильтровать занятия по направлению

- **Пояснение:** сужает расписание до нужного танцевального стиля.
- **Актёры:** Пользователь.
- **Предусловия:** расписание загружено (UC-02).
- **Триггер:** пользователь выбирает направление в панели фильтров.
- **Основной поток:**
  1. Пользователь выбирает направление.
  2. Система отбирает занятия этого направления среди загруженных.
  3. Система обновляет список и счётчики.
- **Альтернативные потоки:**
  - А1. Занятий выбранного направления нет: сообщение «Нет занятий по выбранному направлению».
  - А2. Пользователь сбрасывает фильтр: возвращается полный список.
- **Постусловия:** показаны только занятия выбранного направления.
- **Трассировка:** REQ-FUNC-006.

## UC-13: Просмотреть информацию о преподавателе

- **Пояснение:** помогает выбрать занятие или тренера по его описанию.
- **Актёры:** Пользователь.
- **Предусловия:** выбрано занятие или открыта карточка преподавателя.
- **Триггер:** пользователь нажимает на имя преподавателя.
- **Основной поток:**
  1. Пользователь нажимает на имя преподавателя.
  2. Система загружает данные преподавателя.
  3. Система показывает фотографию, биографию и ближайшие занятия.
- **Альтернативные потоки:**
  - А1. Фотография не загружена: показывается изображение-заглушка.
- **Постусловия:** пользователь ознакомился с информацией о преподавателе.
- **Трассировка:** REQ-FUNC-008.

### 5. Границы текущей модели

1. На диаграмме прецедентов один человеческий актёр «Пользователь». Роль «Администратор» из SRS в этой итерации не показана.
2. Прецеденты UC-01, UC-05, UC-08–UC-10 описаны текстом, но подробных диаграмм поведения для них нет; модель динамики построена вокруг записи на групповое занятие.
3. Email-подтверждение (REQ-INT-005) в SRS помечено как «отложено», поэтому на диаграммах не показано; правило BR-10 заготовлено для следующей итерации.
4. Диаграмма состояний описывает процесс оформления записи; полный жизненный цикл статуса записи («Активна», «Отменена учеником», «Посещена») приведён в SDD 2.2.11.
