## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}

Настоящий документ представляет собой Спецификацию требований к программному обеспечению (SRS) для веб-приложения «RhythmSpace». Его главная задача — четко определить границы проекта и зафиксировать **ЧТО** именно должна делать система. Документ выступает ориентиром для команды разработки, тестировщиков и заказчика.

### 1.2 Область применения продукта {#12-product-scope}

**«RhythmSpace»** 0.1 — веб-приложение для автоматизации работы школы танцев. Платформа позволяет ученикам просматривать актуальное расписание, записываться на групповые занятия и отслеживать прогресс, а администраторам — управлять расписанием и списками групп.

**Входит в область применения:** регистрация и авторизация, ведение расписания, онлайн-запись, личный профиль ученика, статистика прогресса, фильтрация по направлениям и филиалам.
**Не входит в область применения:** онлайн-оплата абонементов, интеграция с фитнес-трекерами, разработка нативных мобильных приложений.

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

**«RhythmSpace»** — новый самостоятельный продукт. Ранее управление школой танцев требовало использования бумажных журналов, мессенджеров и Excel-таблиц. Приложение объединяет эти процессы в едином цифровом пространстве.

**Внешние системы и зависимости:**
* **СУБД PostgreSQL** — для хранения данных.
* **SMTP-сервер** — для отправки email-уведомлений.

### 2.2 Функции продукта {#22-product-functions}

Основные функциональные возможности веб-приложения «RhythmSpace»:
* Формирование и отображение расписания групповых занятий (день, время, направление, преподаватель).
* Онлайн-запись на тренировки с возможностью отмены брони.
* Создание личного профиля ученика с указанием уровня подготовки.
* Ведение статистики прогресса (учет посещений и достижений).
* Выбор конкретного филиала (студии) сети школы танцев.
* Поиск и фильтрация занятий по танцевальным направлениям.
* Отображение количества свободных мест в группе.
* Просмотр детальной информации о преподавателе.

### 2.3 Ограничения продукта {#23-product-constraints}

* **Только веб-версия:** без нативных приложений.
* **Язык интерфейса:** русский.
* **Законодательство:** соответствие Закону РБ «О защите персональных данных».
* **Технологический стек:** Java (Spring Boot) + React + PostgreSQL.

### 2.4 Характеристики пользователей {#24-user-characteristics}

| Роль | Описание | Права доступа |
| :--- | :--- | :--- |
| **Администратор** | Сотрудник школы | Создание и редактирование расписания, просмотр всех записей |
| **Ученик** | Клиент школы | Просмотр расписания, запись, отмена, просмотр профиля |

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

**Допущения:** пользователи используют современные браузеры; школа имеет стабильное интернет-соединение.
**Зависимости:** SMTP-сервер для отправки писем (при сбое ученик не получит подтверждение).

## 3. Требования {#3-requirements}

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

**REQ-INT-001: Главная страница (Расписание)**
* **Statement:** Система должна предоставлять главную страницу со списком предстоящих занятий, панелью фильтров и виджетом краткой статистики.
* **Verification Method:** Demonstration.

**REQ-INT-002: Экран «Мои занятия»**
* **Statement:** Система должна предоставлять экран с активными записями, списком достижений и историей посещений.
* **Verification Method:** Demonstration.

**REQ-INT-003: Интерфейс администратора**
* **Statement:** Система должна предоставлять интерфейс для создания и редактирования занятий (только для Администратора).
* **Verification Method:** Test.

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

**REQ-INT-004: Адаптивность**
* **Statement:** Система должна корректно отображаться на экранах от 320px до 2560px.
* **Verification Method:** Test.

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

**REQ-INT-005: Отправка email**
* **Statement:** Система должна отправлять email-подтверждения при успешной записи.
* **Verification Method:** Test.

**REQ-INT-006: REST API**
* **Statement:** Бэкенд должен предоставлять REST API (JSON) для взаимодействия с React-фронтендом.
* **Verification Method:** Test (Postman).

### 3.2 Функциональные требования {#32-functional}

**REQ-FUNC-001: Авторизация**
* **Statement:** Система должна обеспечивать вход по email и паролю с разделением ролей.
* **Verification Method:** Test.

**REQ-FUNC-002: Отображение расписания**
* **Statement:** Система должна формировать и отображать расписание групповых занятий с указанием дня, времени, направления и преподавателя.
* **Acceptance Criteria:** Карточки занятий отображаются в хронологическом порядке.
* **Verification Method:** Demonstration.

**REQ-FUNC-003: Запись и отмена**
* **Statement:** Система должна позволять ученику записываться на тренировку при наличии мест и отменять запись.
* **Acceptance Criteria:** При нажатии «Записаться» счетчик мест уменьшается; кнопка меняется на «Отменить».
* **Verification Method:** Test.

**REQ-FUNC-004: Профиль и прогресс**
* **Statement:** Система должна создавать личный профиль ученика с указанием уровня подготовки и вести статистику прогресса (учет посещений и достижений).
* **Acceptance Criteria:** В профиле отображается актуальный уровень и список достижений.
* **Verification Method:** Demonstration.

**REQ-FUNC-005: Выбор филиала**
* **Statement:** Система должна предоставлять возможность выбора конкретного филиала (студии) сети школы танцев для просмотра расписания.
* **Verification Method:** Test.

**REQ-FUNC-006: Поиск и фильтрация**
* **Statement:** Система должна обеспечивать поиск и фильтрацию занятий по танцевальным направлениям.
* **Acceptance Criteria:** При выборе фильтра «Хип-хоп» в списке остаются только соответствующие занятия.
* **Verification Method:** Test.

**REQ-FUNC-007: Свободные места**
* **Statement:** Система должна отображать количество свободных мест в группе на карточке занятия.
* **Verification Method:** Test.

**REQ-FUNC-008: Информация о преподавателе**
* **Statement:** Система должна предоставлять возможность просмотра детальной информации о преподавателе (имя, фото, описание опыта).
* **Verification Method:** Demonstration.

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

**REQ-PERF-001: Загрузка страниц**
* **Statement:** Время загрузки главной и личного кабинета не должно превышать 2 секунд.
* **Verification Method:** Test.

**REQ-PERF-002: Отклик API**
* **Statement:** Время обработки запроса к REST API не должно превышать 300 мс для 90% запросов.
* **Verification Method:** Analysis.

#### 3.3.2 Безопасность {#332-security}

**REQ-SEC-001: Хеширование паролей**
* **Statement:** Пароли должны храниться в виде хешей BCrypt.
* **Verification Method:** Inspection.

**REQ-SEC-002: Разграничение прав (RBAC)**
* **Statement:** Доступ к управлению расписанием только для роли Администратор.
* **Verification Method:** Test.

#### 3.3.3 Надёжность {#333-reliability}

**REQ-REL-001: Обработка ошибок внешних сервисов**
* **Statement:** При недоступности SMTP-сервера система не должна «падать», ошибка логируется.
* **Verification Method:** Test.

#### 3.3.4 Доступность {#334-availability}

**REQ-AVAIL-001: Уровень доступности**
* **Statement:** Доступность системы не менее 99% в месяц.
* **Verification Method:** Analysis.

#### 3.3.5 Наблюдаемость {#335-observability}

**REQ-OBS-001: Логирование**
* **Statement:** Все события бэкенда логируются с датой, временем и уровнем важности.
* **Verification Method:** Inspection.

### 3.4 Соответствие стандартам {#34-compliance}

**REQ-COMP-001: Защита персональных данных**
* **Statement:** Обработка данных в соответствии с Законом РБ «О защите персональных данных».
* **Verification Method:** Inspection.

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}

**REQ-INST-001: Контейнеризация**
* **Statement:** Бэкенд и БД должны поставляться в Docker-контейнерах (docker-compose).
* **Verification Method:** Demonstration.

#### 3.5.2 Сборка и поставка {#352-build-and-delivery}

**REQ-BUILD-001: Сборка**
* **Statement:** Сборка бэкенда через Maven (`mvn clean package`), фронтенда через `npm run build`.
* **Verification Method:** Test.

#### 3.5.3 Распределение {#353-distribution}

**REQ-DIST-001: Централизованное развертывание**
* **Statement:** Все компоненты размещаются на одном сервере.
* **Verification Method:** Inspection.

#### 3.5.4 Сопровождаемость {#354-maintainability}

**REQ-MAINT-001: Использование Git**
* **Statement:** Разработка ведется в Git с использованием веток и Pull Request.
* **Verification Method:** Inspection.

#### 3.5.5 Повторное использование {#355-reusability}

**REQ-REUSE-001: UI-компоненты**
* **Statement:** Интерфейсные элементы реализуются как переиспользуемые React-компоненты.
* **Verification Method:** Inspection.

#### 3.5.6 Переносимость {#356-portability}

**REQ-PORT-001: Независимость от ОС**
* **Statement:** Работоспособность на Windows, Linux, macOS при наличии Docker.
* **Verification Method:** Demonstration.

#### 3.5.7 Стоимость {#357-cost}

**REQ-COST-001: Open Source**
* **Statement:** Использование бесплатных технологий (Spring Boot, PostgreSQL, React).
* **Verification Method:** Inspection.

#### 3.5.8 Сроки {#358-deadline}

**REQ-DEAD-001: Этапы**
* **Statement:** Проект разбит на 4 этапа (анализ, ядро, интеграции, тестирование).
* **Verification Method:** Analysis.

#### 3.5.9 Доказательство концепции {#359-proof-of-concept}

**REQ-POC-001: Прототип записи**
* **Statement:** До начала разработки создается прототип записи на занятие.
* **Verification Method:** Demonstration.

#### 3.5.10 Управление изменениями {#3510-change-management}

**REQ-CM-001: Pull Request**
* **Statement:** Слияние в `main` только через Pull Request.
* **Verification Method:** Inspection.
