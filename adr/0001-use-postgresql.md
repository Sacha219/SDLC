# Использование PostgreSQL в качестве основной СУБД

## Контекст и постановка задачи
Приложению «RhythmSpace» необходимо надежно хранить связанные данные (пользователи, расписание занятий, записи учеников, филиалы). Критически важно исключить ситуацию овербукинга (двойной записи на последнее место), для чего требуется поддержка транзакций (ACID). Какую СУБД выбрать?

## Драйверы решения
* **Целостность данных:** Требуется поддержка ACID и внешних ключей.
* **Интеграция:** Необходима совместимость со Spring Data JPA (Hibernate).
* **Бюджет:** Использование Open Source решений.

## Рассмотренные варианты
* PostgreSQL
* MySQL
* MongoDB (NoSQL)

## Итог решения
Выбран вариант **«PostgreSQL»**, потому что он наилучшим образом обеспечивает строгую типизацию и целостность связанных данных, что критично для учета записей.

### Последствия
* **Хорошо:** надежное хранение данных, поддержка сложных связей и транзакций для защиты от овербукинга.
* **Плохо:** требует больше ресурсов памяти, чем SQLite, но это оправдано для production.

### Подтверждение
Проверка наличия зависимостей `spring-boot-starter-data-jpa` и `org.postgresql` в файле `pom.xml`.

## Плюсы и минусы вариантов
### PostgreSQL
* **Хорошо:** поддерживает сложные связи и транзакции.
* **Плохо:** большее потребление памяти.

### MySQL
* **Хорошо:** высокая скорость простых операций.
* **Плохо:** уступает PostgreSQL в работе с JSON и сложными запросами.

### MongoDB
* **Хорошо:** гибкая структура.
* **Плохо:** отсутствие строгих связей (JOIN), что усложняет контроль записей.

## Дополнительная информация
Адресует требования SRS: REQ-FUNC-003 (логика записи), REQ-FUNC-004 (профиль). Связано с ADR-002 (выбор бэкенда).
