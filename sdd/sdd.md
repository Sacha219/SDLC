## 1. Введение {#1-introduction}
### 1.1 Назначение документа {#11-document-purpose}
Настоящий документ (Software Design Description, SDD) описывает архитектуру, структуру компонентов и дизайн веб-приложения RhythmSpace. Документ предназначен для команды разработчиков, которая будет реализовывать систему, а также для сопровождающего персонала (для понимания устройства системы при дальнейшей поддержке).

Документ опирается на ранее согласованную спецификацию требований (SRS), в которой описано, что должна делать система, а SDD отвечает на вопрос, как она будет устроена технически.

### 1.2 Область применения {#12-subject-scope}
Веб-приложение RhythmSpace (версия 1.0) предназначено для автоматизации работы школы танцев.

Ключевые возможности системы включают ведение расписания групповых занятий, онлайн-запись учеников, отображение информации о преподавателях и филиалах, а также ведение профиля ученика с трекером прогресса (учет посещений и достижений).

В область применения данного SDD входит описание клиент-серверной архитектуры, структуры базы данных и используемых технологий. Документ не содержит подробного описания пользовательских интерфейсов (UI/UX-дизайн), поскольку они описаны в отдельной спецификации макетов (SysMLv2).

## 2. Обзор дизайна {#2-design-overview}
### 2.1 Задачи стейкхолдеров {#21-stakeholder-concerns}
В проекте «RhythmSpace» можно выделить следующих ключевых стейкхолдеров и их интересы, связанные с архитектурой:
* **Разработчики:** заинтересованы в понятной модульной структуре, четком разделении слоев (Frontend/Backend) и удобстве сопровождения кода.
* **Заказчик (владелец школы):** заинтересован в том, чтобы архитектура обеспечивала выполнение функциональных требований (онлайн-запись, расписание) и была экономически эффективной.
* **Конечные пользователи (Ученики):** заинтересованы в высокой скорости работы приложения и надежности (сохранность данных о записях).

### 2.2 Выбранные точки зрения {#22-selected-viewpoints}
Для описания архитектуры системы были выбраны следующие точки зрения:

#### 2.2.1 Контекст {#221-context}
Система RhythmSpace взаимодействует со следующими внешними объектами:
* Пользователь: взаимодействует через браузер (ввод данных, просмотр расписания).
* Внешние сервисы: SMTP-сервер (для отправки email-подтверждений о записи).

#### 2.2.2 Композиция {#222-composition}
Система разделена на три основных компонента:
* Фронтенд (SPA на React): отвечает за пользовательский интерфейс.
* Бэкенд (REST API на Spring Boot): содержит бизнес-логику и обрабатывает запросы.
* База данных (PostgreSQL): отвечает за хранение и целостность данных.

#### 2.2.3 Логическое представление {#223-logical}
В бэкенде используется паттерн MVC. Основные классы абстракций: сущности Entity (User, Lesson, Booking), сервисы Service (обработка логики записи) и контроллеры Controller. Во фронтенде используются функциональные React-компоненты.

#### 2.2.4 Физическое представление {#224-physical}
На этапе MVP физическая инфраструктура представлена одним виртуальным сервером (VPS), на котором развернуты Docker-контейнеры.

#### 2.2.5 Структура {#225-structure}
Бэкенд-приложение организовано в виде пакетов: controller, service, repository, entity. Это обеспечивает слабую связанность (low coupling) и высокую связность (high cohesion).

#### 2.2.6 Зависимости {#226-dependency}
Фронтенд зависит от бэкенда (через REST API). Бэкенд зависит от базы данных (через Hibernate/JPA) и внешнего SMTP-сервера. Направление зависимостей строго контролируется: контроллеры вызывают сервисы, сервисы вызывают репозитории.

#### 2.2.7 Информация {#227-information}
Основные сущности базы данных: Users (ученики и админы), Lessons (занятия), Bookings (записи), Teachers (преподаватели), Branches (филиалы). Связи реализуются через внешние ключи.

#### 2.2.8 Интерфейс {#228-interface}
Основным интерфейсом является REST API (JSON), через который Frontend получает данные от Backend. Также используются интерфейсы внешних сервисов (SMTP).

#### 2.2.9 Взаимодействие {#229-interaction}
Типовой сценарий: Ученик нажимает «Записаться» -> React отправляет POST-запрос -> Контроллер вызывает Сервис -> Сервис проверяет лимит мест и сохраняет данные в БД -> Фронтенд показывает сообщение об успехе.

#### 2.2.10 Алгоритм {#2210-algorithm}
В системе реализована логика проверки свободных мест при записи. Сервис проверяет текущее количество броней (booked_count) и сравнивает с максимальной вместимостью группы (capacity).

#### 2.2.11 Динамика состояний {#2211-state-dynamics}
Основные состояния системы связаны с бронированием: «Активна», «Отменена учеником», «Посещена». Переход между состояниями осуществляется в зависимости от действий пользователя и подтверждения тренером.

#### 2.2.12 Параллелизм {#2212-concurrency}
Используется многопоточность Spring Boot. Для предотвращения race condition (когда два пользователя занимают одно последнее место) используются транзакции БД и механизм оптимистичных блокировок в JPA.

#### 2.2.13 Паттерны {#2213-patterns}
Применяются паттерны: MVC (Model-View-Controller), Repository, DTO (Data Transfer Object), а также компонентный подход во фронтенде (React).

#### 2.2.14 Развёртывание {#2214-deployment}
Все компоненты развертываются на одном сервере (VPS). Frontend раздается через Nginx. Backend и БД запущены в Docker-контейнерах.

#### 2.2.15 Ресурсы {#2215-resources}
Основным ограниченным ресурсом является оперативная память сервера. Сложное управление пулами потоков не требуется, так как нагрузка невысокая (до 500 пользователей).

## 3. Проектные представления {#3-design-views}
В данном разделе описаны ключевые проектные представления системы «RhythmSpace».

### 3.1 Представление: Схема базы данных {#31-data-model}
*ID: VIEW-001-DataModel*
База данных реализуется на PostgreSQL. Основные сущности и их атрибуты:
* `users` (id, email, password_hash, name, role, level);
* `branches` (id, name, address);
* `teachers` (id, name, bio, photo_url);
* `lessons` (id, branch_id, teacher_id, style, start_time, max_students, booked_count);
* `bookings` (id, user_id, lesson_id, booking_date, status);
* `achievements` (id, user_id, title, date_earned).
Связи: lessons имеет связь «один-ко-многим» с bookings. users связан с bookings. teachers связан с lessons.
*More Information:* Реализует требования REQ-FUNC-002, REQ-FUNC-003, REQ-FUNC-004.

### 3.2 Представление: Слои Backend (MVC) {#32-backend-layers}
*ID: VIEW-002-BackendLayers*
Серверная часть на Spring Boot разделена на 4 уровня:
* **Controller:** классы с аннотацией @RestController (LessonController, BookingController, AuthController).
* **Service:** классы с аннотацией @Service (LessonService, BookingService, AuthService). Содержат бизнес-логику.
* **Repository:** интерфейсы, наследуемые от JpaRepository.
* **Entity:** Java-классы, маппящиеся на таблицы БД (User, Lesson, Booking, Teacher).
Направление вызовов: контроллер -> сервис -> репозиторий -> база данных.
*More Information:* реализует требования REQ-FUNC-001, REQ-FUNC-007.

### 3.3 Представление: Компоненты Frontend {#33-frontend-components}
*ID: VIEW-003-FrontendComponents*
Клиентская часть (React) организована следующим образом:
* `pages/`: Экраны приложения (DashboardPage, MyLessonsPage, LoginPage).
* `components/`: Переиспользуемые UI-элементы (Header, Footer, LessonCard, FilterPanel).
* `api/`: Модули для отправки HTTP-запросов к Backend.
* `context/`: Глобальное состояние авторизации пользователя (AuthContext).
*More Information:* Реализует требования REQ-INT-001, REQ-INT-002, REQ-INT-004.

### 3.4 Представление: Внешние интеграции {#34-external-integrations}
*ID: VIEW-004-ExternalIntegrations*
Бэкенд интегрируется со следующими внешними сервисами:
* **SMTP-сервер:** отправка email-подтверждений при успешной записи на тренировку (через JavaMailSender). Все ключи API и пароли хранятся в переменных окружения.
*More Information:* Реализует требования REQ-INT-005.

## 4. Решения {#4-decisions}
В данном разделе зафиксированы ключевые архитектурные решения. Подробные обоснования хранятся в папке adr/ репозитория.

### 4.1 Выбор СУБД PostgreSQL {#41-database}
*ID: DEC-001-Database*
* **Context:** Приложению необходимо надежно хранить связанные данные (пользователи, занятия, записи). Требуется поддержка транзакций (ACID).
* **Options:** PostgreSQL, MySQL, MongoDB.
* **Outcome:** Выбран PostgreSQL, так как он обеспечивает строгую типизацию и имеет зрелую интеграцию со Spring Data JPA.
* **More Information:** Ссылка на полный документ ADR-0001.

### 4.2 Выбор бэкенд-фреймворка Spring Boot {#42-backend}
*ID: DEC-002-Backend*
* **Context:** Требуется создать надежное, безопасное и масштабируемое REST API.
* **Options:** Java + Spring Boot, Node.js + Express, Python + Django.
* **Outcome:** Выбран Spring Boot, так как он предоставляет встроенные механизмы безопасности (Spring Security) и удобную работу с БД через JPA.
* **More Information:** Ссылка на полный документ ADR-0002.

### 4.3 Выбор фронтенд-библиотеки React {#43-frontend}
*ID: DEC-003-Frontend*
* **Context:** Необходимо создать быстрый, интерактивный и адаптивный интерфейс (SPA).
* **Options:** React, Vue.js, Angular.
* **Outcome:** Выбран React, так как он позволяет создавать переиспользуемые компоненты и обеспечивает высокую скорость рендеринга благодаря Virtual DOM.
* **More Information:** Ссылка на полный документ ADR-0003.
