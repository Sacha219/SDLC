## 1. Введение

### 1.1 Назначение документа
Настоящий документ (Software Design Description, SDD) описывает архитектуру, структуру компонентов и дизайн веб-приложения «RhythmSpace». Документ предназначен для команды разработчиков, которая будет реализовывать систему, а также для сопровождающего персонала. Документ опирается на ранее согласованную спецификацию требований (SRS) и отвечает на вопрос, как она будет устроена технически.

### 1.2 Область применения
Веб-приложение RhythmSpace (версия 1.0) предназначено для автоматизации работы школы танцев. Ключевые возможности системы включают ведение расписания групповых занятий, онлайн-запись учеников, ведение профиля с указанием уровня подготовки и отслеживание прогресса (посещений и достижений). 
В область применения данного SDD входит описание клиент-серверной архитектуры, структуры базы данных и используемых технологий.

## 2. Обзор дизайна

### 2.1 Задачи стейкхолдеров
* **Разработчики:** заинтересованы в понятной модульной структуре и четком разделении слоев.
* **Заказчик (владелец школы):** заинтересован в том, чтобы архитектура обеспечивала надежное расписание и исключала овербукинг (двойную запись).
* **Пользователи (ученики):** заинтересованы в быстрой загрузке расписания и удобном интерфейсе записи.

### 2.2 Выбранные точки зрения
* **Контекст:** Система взаимодействует с Пользователем (браузер) и SMTP-сервером (отправка email-подтверждений).
* **Композиция:** Приложение разделено на Frontend (React), Backend (Spring Boot) и Базу данных (PostgreSQL).
* **Логическое представление:** На бэкенде используется паттерн MVC (Controller, Service, Repository, Entity). На фронтенде — компонентный подход.
* **Физическое представление:** Всё развернуто на одном сервере с использованием Docker-контейнеров.
* **Информация:** Основные сущности — Ученик, Занятие, Запись, Преподаватель.
* **Взаимодействие:** Пользователь нажимает «Записаться» -> React отправляет POST-запрос -> Контроллер валидирует данные -> Сервис проверяет наличие мест -> Репозиторий сохраняет запись в БД.
* **Параллелизм:** Важный аспект при записи на занятия. Используются транзакции БД для предотвращения ситуации, когда два ученика одновременно записываются на последнее место.

## 3. Проектные представления

### 3.1 Представление: Схема базы данных
*ID: VIEW-001-DataModel*
База данных реализуется на PostgreSQL. Основные сущности:
* `users` (id, email, password_hash, name, role, level).
* `branches` (id, name, address) — филиалы.
* `teachers` (id, name, bio, photo_url).
* `lessons` (id, branch_id, teacher_id, style, start_time, duration, max_students, booked_count).
* `bookings` (id, user_id, lesson_id, booking_date).
* `achievements` (id, user_id, title, date_earned).

Связи: `lessons` имеет связь «один ко многим» с `bookings`. `users` связан с `bookings`. Схема создается через Hibernate.

### 3.2 Представление: Слои Backend (MVC)
*ID: VIEW-002-BackendLayers*
Серверная часть разделена на слои:
* **Controller:** Классы `@RestController` (AuthController, LessonController). Принимают HTTP-запросы.
* **Service:** Классы `@Service` (BookingService, LessonService). Содержат бизнес-логику, включая проверку лимита мест.
* **Repository:** Интерфейсы `JpaRepository` для доступа к БД.
* **Entity:** Java-классы (User, Lesson, Booking).
Направление вызовов: Controller -> Service -> Repository.

### 3.3 Представление: Компоненты Frontend
*ID: VIEW-003-FrontendComponents*
Клиентская часть (React) организована так:
* `pages/`: Экраны (DashboardPage, MyLessonsPage, LoginPage).
* `components/`: UI-элементы (LessonCard, BranchSelector, FilterPanel).
* `api/`: Модули для отправки запросов к Backend (axios).
* `context/`: Глобальное состояние (AuthContext для хранения токена).

### 3.4 Представление: Внешние интеграции
*ID: VIEW-004-ExternalIntegrations*
Бэкенд интегрируется с SMTP-сервером (через `JavaMailSender`) для отправки email-подтверждений при успешной записи на тренировку.

## 4. Решения

### 4.1 Выбор СУБД PostgreSQL
*ID: DEC-001-Database*
* **Контекст:** Необходимо надежно хранить данные о пользователях, расписании и записях.
* **Решение:** PostgreSQL.
* **Обоснование:** Обеспечивает строгую типизацию и отлично работает со связанными данными (One-to-Many). Имеет зрелую интеграцию со Spring Data JPA. (См. ADR-001).

### 4.2 Выбор бэкенд-фреймворка Spring Boot
*ID: DEC-002-Backend*
* **Контекст:** Требуется надежное и безопасное REST API.
* **Решение:** Java + Spring Boot 3.
* **Обоснование:** Предоставляет встроенные механизмы безопасности (Spring Security, JWT) и высокую производительность. (См. ADR-002).

### 4.3 Выбор фронтенд-библиотеки React
*ID: DEC-003-Frontend*
* **Контекст:** Необходим быстрый и интерактивный интерфейс без перезагрузок страницы.
* **Решение:** React (Vite).
* **Обоснование:** Позволяет создавать переиспользуемые компоненты и обеспечивает высокую скорость рендеринга благодаря Virtual DOM. (См. ADR-003).
